# ADR-0012: Release Candidate Boundary and the Two-Channel Readiness Gate

- **Status**: Accepted (2026-10-20)
- **Decision basis**: Semantic Versioning 2.0; the generated-file policy in [`CONTRIBUTING.md`](../../CONTRIBUTING.md); `scripts/release/version-check.ts`; the stable-release gates in [`ROADMAP.md`](../../ROADMAP.md); ADR-0008 (no packaging/signing/notarization), ADR-0011 (ACP adapter blocked).
- **Scope of this ADR**: why the workspace moves to `1.0.0-rc.1`, exactly what an RC does and does not authorize, and why a stable `1.0.0` still needs an explicit, separate admission decision. **No artifact is published, tagged, signed, or notarized by this decision.**

## Context

The v1 candidate — P0 kernel, runtime, headless CLI, local Run Protocol, extension SDK, engineering scenario pack, bilingual docs — has accumulated in the working tree at version `0.0.0`. The release tooling (`scripts/release/`) already generates an offline SBOM and a reproducible build-info, and its readiness checker already refused to treat a plain `1.0.0` as ready without explicit blessing. What was missing was an explicit answer to a narrower question: how do we publish a *release candidate* for that candidate without (a) hand-editing generated artifacts or lockfiles, and (b) sliding into claiming a stable 1.0.0 before the acceptance gates in the ROADMAP are actually closed?

## Decision

1. **Cut `1.0.0-rc.1` as the workspace version.** Root and every `packages/*` package move to `1.0.0-rc.1` through one authoritative script — `scripts/release/bump-version.ts <version>` — which rewrites only the `version` field of each package.json and touches nothing else. Generated artifacts (`dist/release/sbom.json`, `dist/release/build-info.json`) are then regenerated by their own generators, and the lockfile by `pnpm install`; neither is ever hand-edited.

2. **Two readiness channels.** `version-check.ts` derives a channel from the version:
   - **rc channel** (any prerelease suffix, e.g. `1.0.0-rc.1`) may pass the readiness gate as a *local RC artifact build*. The new `rc_boundary` gate states on the record what this channel does and does not authorize.
   - **stable channel** (plain `1.0.0`) additionally requires the explicit `--allow-1.0` blessing. RC builds passing the gate do *not* graduate to stable; graduation is a separate human decision, made only after the ROADMAP acceptance gates (including the reproducible efficacy scorecard) close.

3. **An RC authorizes only the local, offline posture that already exists.** A `1.0.0-rc.1` build means: the workspace version is coherent, offline SBOM + build-info regenerate reproducibly, and the offline `keystone ci` proof smoke runs green. It is a developer-preview, CLI-first artifact.

4. **An RC does NOT authorize, and this tree must not claim, any of the following** — they stay unverified until independently proven:
   - end-to-end suite on a real Windows machine (the `spawn` resolver is implemented and unit-tested only);
   - Apple code signing, notarization, or a packaged universal `.app`. A source-tree Swift/WKWebView host is implemented and locally exercised (ADR-0008), but it is not signed, notarized, or distributed; the checked local helper is Apple-silicon only and release architectures must rebuild from source;
   - live interoperability with any real model vendor — native wire adapters are mock-`fetch` tested only, and the Builder Loop still drives the validated text envelope;
   - an ACP adapter (blocked, ADR-0011: no adapter ships);
   - a hosted CI runner being green — the CI workflows are defined but not treated as evidence here.

5. **Package release version is not a protocol version.** The `keystone.*` schema `schemaVersion` values (e.g. `keystone.run.event@1.0.0`) and `keystone.run.protocol@1.2.0` are independent contract versions and are untouched by this release bump (GOVERNANCE §4). Protocol 1.2.0 is the additive risk-graded startup revision recorded in ADR-0013. Bumping the package RC does not bump, break, or stabilize any on-wire contract.

## Consequences

- Contributors now have one sanctioned version-movement path: `pnpm run release:bump <version>`, then `pnpm run release:all`. There is no third path.
- The readiness report prints the channel (`rc` vs `stable`) and the boundary detail every time, so a future `1.0.0` attempt without `--allow-1.0` fails loudly rather than silently shipping.
- The RC is a pre-stable semver prerelease: consumers should treat it as unreleased software, and the root package remains `private` — nothing on npm or any registry.
- When the ROADMAP gates close, the stable cut is a deliberate next change: drop the prerelease suffix, re-run `release:all`, and pass `--allow-1.0` at that moment — not before.
