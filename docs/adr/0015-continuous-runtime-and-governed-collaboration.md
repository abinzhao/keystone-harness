# ADR-0015: Continuous runtime and governed collaboration

Date: 2026-10-21

Status: Accepted for local implementation under the previously approved iteration architecture and the M4–M8 continuation request. External deployment and stable release are separate decisions.

## Context

M0–M3 provides a local workbench and lease-gated execution. M4–M8 requires durable cognition, honest context accounting, actual recovery, extension lifecycle, portable proofs, collaboration and reproducible release evaluation.

## Decision

1. Project facts and experience are event-derived projections. KernelSession commits validated events before applying projections. Reopening a session repairs interrupted projection writes. Project operations serialize on a project lock, preserve user-confirmed frozen entries and reject model-origin promotion without an eligible basis.
2. Context includes the actual current Contract, source and scope metadata. Budget admission counts the entire rendered capsule, including mandatory constraints and wrappers. Character estimates are labelled estimates; provider usage alone is billed as measured tokens. Cache identities cover full content. Cached parsing avoids actual repeated parsing, and no token saving is invented.
3. A persisted run binding records the workspace, mode, configuration and checkpoint needed to restart the Builder/Assurance loop. Recovery first verifies ledger, snapshot and artifacts. Interrupted actions are observations to reconcile, never automatically replayed side effects. A selected checkpoint forks only its event prefix; subsequent writes and verification use an independent workspace and fresh leases.
4. Proof exploration consumes kernel output. Baseline/candidate comparison uses separate workspaces and protected checks. A signature proves author and byte integrity, not satisfaction of a Contract. Imported remote results remain untrusted observations until local kernel admission and verification.
5. Extension management separates static review, explicitly authorized probes, registration and activation. Registry activation grants no capabilities. Execution intersects manifest ceilings with the task envelope and passes through the existing lease boundary. Disabled or changed extensions cannot silently continue in a new task. Skills load progressively and never authorize their scripts.
6. Remote delegation and shared project information are opt-in. Each request binds identity, resources, parameters, budget, expiry and cancellation. Transport errors do not create success. Parent completion requires local verification; child success never changes the parent state directly.
7. Evaluation uses fixed, versioned fixtures, independent acceptance, repetitions and honest missing metrics. Desktop packaging generates reproducible universal binaries where the toolchain supports both targets. Signing, notarization, real-provider acceptance and hosted CI are reported as gates requiring observed external evidence.
8. Historical forks require an exact local workspace recovery capsule, distinct from the metadata-only onboarding snapshot. The capsule contains a bounded Git binary patch and ordinary untracked files, stays in the local content-addressed store, and is referenced by a checkpoint event. Credential-shaped paths, symlinks, oversized inputs and index/ignored-file mismatches make executable forking unavailable; it never guesses HEAD as the selected checkpoint. A user-requested fork creates an independent worktree through a fresh kernel lease. Recovery capsules are not exported implicitly as portable collaboration bundles.
9. Isolated-workspace provisioning waits for the task Contract to be accepted and started. A parameter-bound `git.write` lease admits creation of the managed detached worktree for the task's existing writable scope; provisioning never grants the Builder access to additional paths. Read-only or unapproved Contracts cannot provision an executable worktree. Restoring checkpoint file bytes additionally requires `fs.write` admission for every restored path. A fork carries the original content baseline, but binds its baseline fingerprint to the detached Git identity so an unchanged historical workspace does not acquire a false stale-evidence signal.
10. Each step reloads the event-derived experience projection and selects against the current Contract. Evaluation names only entries actually admitted into a rendered Context Plan. Repository rules are mandatory scoped facts; removed or changed sources are refreshed before the next plan, while user-frozen constraints remain protected.
11. A recorded local user decision may reject a quarantined candidate. The existing candidate event payload already carries rejected/expired states; a rejection commits a terminal revision of the same candidate, preserving its source and statement. Candidate issuance, rejection and promotion serialize on a project event lock. Candidate IDs cannot be reused to reactivate terminal revisions, and promotion checks the latest event-derived state and exact candidate content. Clearing unprotected experience rejects pending candidates and revokes entries before deleting their projections. Rebuilt audit rows remain visible but cannot re-enter execution context.
12. Complete portable task export preserves the original ledger and every referenced artifact. Since normal checkpoints reference recovery capsules, a separate explicit source-content opt-in may export supported local capsules after path/size/shape checks. This opt-in is off by default, introduces no network operation and never authorizes imported execution. Capsule-bearing imports remain quarantined; adoption creates a fresh local draft and carries no foreign permissions or completion. A proof-only export remains distinct from a complete portable task bundle.
13. A fresh imported draft may continue only after a separate authenticated local start. Reopening that draft may re-inject the local scenario contract proposer and action resolver because those policies are runtime wiring, not ledger authority. The original `task.created` request and untrusted source reference remain unchanged; the start supplies a new local autonomy envelope, configuration snapshot and explicit confirmation, while no foreign Contract, lease, Evidence, Proof or completion state is reused.
14. Each Builder Context Plan binds refreshed cognition and its retriever to the same observed workspace snapshot. Checkpoint metadata uses that plan's observation; an earlier onboarding snapshot must not exclude current mandatory rules. Frozen local user constraints retain their existing admission protection, and branch-local scanning never rewrites primary project knowledge.
15. Portable branch bundles retain inherited parent events byte-for-byte. Validation accepts only hash-linked, committed `branch.created` transitions from the current branch to a distinct child whose checkpoint belongs to the inherited prefix. The manifest names the final selected logical branch; arbitrary branch-ID changes and foreign task events remain refused. Import still creates only a quarantined candidate, with no replay into local authority.
16. Preview, user confirmation and task start use one immutable request and permission snapshot. Editing scope, commands, access or confirmation policy invalidates pending consent. A workbench child-branch resume names that exact branch and displays branch-owned state; it cannot substitute primary-task completion.
17. Standalone local consent remains a recorded user decision without an invented intervention identity. Proof projection lists only decisions carrying an actual intervention ID in its intervention summary; the complete ledger retains every standalone consent event and its lease binding. This changes neither state folding nor completion decisions and keeps `keystone.proof.package@1.0.0` fields unchanged. Conformance verifies valid export, unchanged authority, and replay of a draft-adoption consent.
18. Branch comparison ranks the same current Proof shown in its branch card. Historical task status stays separately visible, but changed or unavailable workspaces cannot retain a current `proven` ranking or a satisfied verification summary. Refreshed condition verdicts and residual risks feed comparison without mutating the ledger, evidence or historical completion events.

## Invariants

| Invariant | Impact and enforcement |
|---|---|
| Model cannot change authority | Facts, experience and remote results enter only validated KernelSession methods. No model-authored completion or permission decision is admitted. |
| Events own state | Commit event first; rebuild projections from events after interruption. Recovery and branches preserve a verifiable event graph. |
| Effects require leases | Model, tools, verifiers, extension calls and remote delegation use parameter-bound leases; recovery obtains new leases. |
| Provenance propagates | Full-content identities, source references and derivation chains survive compression, imports, summaries and forks. Signatures never elevate truth or evidence levels. |
| Extensions cannot escalate | Manifest ceilings only restrict existing envelopes. Installation, activation and conformance cannot replace proof evaluation. |

Re-wiring a local proposer or action resolver on a draft does not alter these invariants: neither object is persisted as authoritative state, and every resulting Contract transition, lease and completion decision is still committed by the kernel.

## Compatibility

Existing schema versions remain readable. Additive optional run/checkpoint metadata and read projections require a minor protocol increment and generated-schema conformance tests. A required new event meaning or incompatible object must use a new major schema and explicit migration; no silent rewriting of old ledgers is permitted.

`keystone.run.branch` advances to 1.1.0 with the same readable field shape: new executable forks commit `branch.created` after the copied prefix, and the fold adopts that event's branch identity. Existing branches without this committed binding stay readable but do not gain executable recovery support. `keystone.runtime.runBinding@1.0.0` is a new content-addressed recovery artifact. Context Plan, Project Fact, Experience and Evidence field schemas remain unchanged; the runtime adds stricter admission and repairs their projections from the existing events. Clients require Run Protocol 1.5.0 for executable branch, cognition, lifecycle, collaboration, fresh-draft continuation, input processing, historical baseline comparison and readiness operations.

`keystone.collaboration.bundle` advances additively to 1.1.0. Its optional `includesRecoveryWorkspace` field is part of the manifest digest; absence preserves the 1.0 behavior and refuses recovery capsules. The outer portable format remains `keystone.task-bundle/1`, so old manifests remain readable without acquiring the new opt-in.

Old tasks without a complete run binding remain readable, replayable and exportable; execution recovery either reconstructs a verifiable binding from existing records or refuses with a specific missing-input reason.

## Verification

Conformance cases cover event-before-projection recovery, frozen-fact protection, candidate exclusion, full capsule budgeting, current-snapshot rule admission, historical checkpoint forks and portable inherited-prefix validation, changed-workspace refusal, fresh leases after restart, extension disable/integrity refusal, remote cancellation/replay/tamper rejection and signature-without-truth elevation. Browser journeys cover task creation, cognition correction, restart, child-branch continuation, branch comparison, extension review and proof export. Deferred preview tests verify that changed permission controls invalidate draft-start consent.
